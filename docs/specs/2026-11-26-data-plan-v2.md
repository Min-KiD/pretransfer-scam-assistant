# Data plan v2: wider scenario catalogue, independent test set, teacher dialogues

From: planner tab. Date: 2026-11-26.
Status: **proposal, not approved.** Nothing here is dispatched. Draft scenario files are in
`docs/specs/scenarios-v2/`; the app does not load them.

## 1. Why

Minh, 26/11: the dataset has few scenarios, and its scam share is too high, while real transfers are mostly ordinary.

State of the data today:

| Set | Scam | Ordinary | Ordinary share |
|---|---|---|---|
| Catalogue (`scenarios/`) | 11 scenarios | 4 scenarios | 27% |
| Test cases (`sim/cases/`) | 220 | 80 | 27% |
| Stories for M3 (`data/E6/cases.jsonl`) | 2,420 | 880 | 27% |

Two further facts that support the request:

- 14 of the 89 real narratives in `data/narr/real/` match no scenario in the catalogue.
- The false-alarm rate is measured on only 80 ordinary cases. For flash-lite, 7 of 80 has a 95% interval of about
  4% to 17%, too wide to choose between models.

What the mix does and does not change:

- The miss rate on scams and the false-alarm rate on ordinary transfers are each measured inside their own group,
  so they do not depend on the mix.
- The mix changes how many warnings are false. Illustration with flash-lite alone (7 of 80 ordinary flagged, 10 of
  220 scams missed): if 1 chat in 100 were a scam, about 1 warning in 10 would be a real scam. The 1 in 100 is an
  assumption; the real share among chats is unknown, because the chat only opens for new or flagged accounts.

## 2. Approach

Agreed with Minh on 26/11:

- Labels come from code: the scenario and the truth table are sampled first; a model only writes the wording.
- The model family that writes the test set takes no part in training.

| Family | Role |
|---|---|
| GPT | Test only: stories for the new test set, new test images |
| Claude Sonnet 5.5 (subscription tab, no API) | Teacher playing the assistant, extra train stories, half of the train-side users |
| Gemini | Existing 3,000 train stories, simulated user, existing Nano Banana images |

Rejected:

- All three families in both train and test: no independent test set.
- Teacher dialogues only, no new test set: fine-tune numbers would be measured on data from the training families.

### 3.4 Checks run on the drafts (26/11)

- All 10 files parse; required keys present; every field is in `core.schema.FIELDS`; every value is in the schema
  or in the list in 3.3; single-select probabilities sum to at most 1.
- Rough distance between field tables (symmetric KL over all fields except `nhan_tai_khoan`). The closest pair in
  the current catalogue is at 12.5 (`gia_co_quan_nha_nuoc` and `gia_ngan_hang`). Three new scenarios are closer
  than that to an existing one:

| New scenario | Nearest | Distance | Same group |
|---|---|---|---|
| `mo_vi_tra_sau_nhan_hoa_hong` | `ctv_online` | 5.9 | yes (both scam) |
| `bt_dat_dich_vu_co_xac_nhan` | `bt_mua_online_nguoi_ban_moi` | 8.1 | yes (both ordinary) |
| `bt_mung_cuoi_gop_quy` | `bt_chuyen_cho_nguoi_than` | 8.3 | yes (both ordinary) |

  Confusion inside a group does not change the label shown to the user; it lowers the "correct scenario" number and
  can weaken M3. No field records that the money sent is borrowed money, which is what sets the pay-later scam apart
  from `ctv_online`. Options: keep it and accept the confusion, fold it into `ctv_online` as a variant, or add a
  field value for it.

### 3.5 Account label

No scenario table sets `nhan_tai_khoan`, so the case generator draws it evenly from five values. In the 300 test
cases, 42 of 220 scam cases and 13 of 80 ordinary cases have the label `quen`, for which the app never opens the
chat (`core/lookup.py`). The drafts follow the existing convention and leave the field out. Whether to sample only
labels that open the chat is an open item for the v2 test set.

### 3.6 Would one extra value separate the pay-later scam from `ctv_online`?

Minh, 26/11: keep all 10 scenarios. He asked whether an extra value removes the confusion, and noted that MoMo
itself knows when the money is a fresh pay-later advance.

Table-level calculation: 4,000 tables sampled per scenario, every field known, most likely scenario among the 25.
This is an upper bound from the tables, not a chat-model measurement; the probabilities given to the new value
(0.75) and the flag (0.9 against 0.03) are the planner's assumptions.

| Variant | Pay-later scam named `ctv_online` | `ctv_online` named pay-later scam | Either named ordinary |
|---|---|---|---|
| Drafts as committed | 11.9% | 11.2% | 0.0% |
| A: `ly_do_tien` gets `tien_vay_chuyen_di` | 7.4% | 6.0% | 0.0% |
| B: system flag "money is a fresh advance" | 4.6% | 3.0% | 0.0% |
| B with half the cases outside MoMo | 10.0% | 8.1% | 0.0% |

- The extra value lowers the confusion; it does not remove it. The confusion never changes the warning label.
- A system flag is the better signal inside MoMo, with limits: it says where the money came from, not why it is
  sent; in the Quảng Nam case the MoMo pay-later advance was 8 of about 122 million VND, the rest came from bank
  loans and instalment purchases MoMo cannot see; the demo has no MoMo data, so the flag would be simulated.
- Variant A is in the drafts (`tien_vay_chuyen_di`). Minh, 26/11, on the proposals of 3.6 and 3.7: "mọi thứ khá
  oke rồi đấy". In the pitch: inside MoMo the system fills this fact.

### 3.7 Noise in the v1 test cases (found 26/11)

- The account label is drawn at random and has nothing to do with the story. 34 of the 80 ordinary cases have a
  receiving account labelled reported or confirmed scam. 123 of the 300 cases have `quen` or `khac`.
- Ordinary cases flagged as scam, split by that label:

| Model | All 80 | 34 cases with a reported or confirmed label | Other 46 |
|---|---|---|---|
| flash-lite | 7 | 5 | 2 |
| Haiku 5.5 | 6 | 3 | 3 |
| `gemma-4-e4b-qat` | 4 | 3 | 1 |
| `qwen3-14b-awq` | 6 | 3 | 3 |

- The generator spreads the unlisted probability mass evenly over all other values. 220 of the 300 cases have at
  least one single-select field with a value its scenario does not list; 95 have two or more. Example:
  `bt_dat_coc_da_xem__12` is labelled ordinary, its table says the money is for a "task" and the account is a
  confirmed scam account, and its opening line is "chuyển gấp tiền nhiệm vụ cho ông bạn". flash-lite answered
  `ctv_online` and that counts as a false alarm.
- Reading the 7 openings flash-lite flagged: at least 3 carry a scam cue in the text itself (task money, an
  investment platform, promised profit). This is the planner's reading.
- Consequence: the v1 false-alarm figures measure this noise as much as the models. The "1 warning in 10" line in
  section 1 uses 7 of 80 and is weakened by it.
- Plan for v2 (accepted in chat by Minh, 26/11; brief `docs/tasks/T4-catalogue-v2.md`, not dispatched):
  - Account label drawn per group, using only labels that open the chat. Ordinary: `moi` 90%, `dang_bi_bao_cao`
    10%, never `da_xac_nhan`. Scam: `moi` 60%, `dang_bi_bao_cao` 25%, `da_xac_nhan` 15%.
  - A rule in code redraws an ordinary table that carries a scam-type detail (install an app, read an OTP, top up
    to withdraw; money for a task, an investment, a "safe account", an error fix, a refund, a forwarded loan; told
    how to answer; threats or secrecy). By this rule 19 of the 80 ordinary test cases and 157 of the 880 ordinary
    train stories carry such a detail. On the 34 ordinary test cases with a clean table and an unflagged account,
    flash-lite flags 2 and Haiku 5.5 flags 2.
  - Test set v2 only: after the rule, a GPT model re-reads each ordinary case and drops those whose text describes
    a scam (the writer invents details for `khac` values, which the rule cannot see). Scam cases are not filtered:
    a scam story that sounds ordinary is the case the assistant exists for.
  - Not M3: it was trained on the same noisy stories, and a graded component must not pick its own exam. Not
    Sonnet either: the teacher family takes no part in the test set.

## 4. Datasets on the v2 catalogue

| Set | Size | Written by | Use |
|---|---|---|---|
| Stories for the 10 new scenarios | 220 each (200 train, 20 val) | flash-lite, existing script `sim/e6_data.py` | M3 retrain, teacher input |
| Teacher dialogues | 60 per scam scenario, 90 per ordinary scenario: 1,800, half ordinary | Sonnet 5.5 as assistant; stories half flash-lite, half Sonnet | LoRA training (E13) |
| Test set v2 | 15 per scam scenario, 25 per ordinary scenario: 475, 53% ordinary | GPT | All chat numbers from here on |
| Old 300 cases | unchanged | flash-lite | Second test set, v1 record |
| Test images | 5-image trial, then 40 | `gpt-image-2.6-sunburst` | Reader check only |

- Only teacher sessions that end on the right scenario are kept.
- Sonnet 5.5 has never been measured as the assistant: run it on 60 stories first.
- Every run with a cost gate or cap uses a seeded stratified case order.

## 5. Order of work

1. Minh approves or cuts the scenario list. The catalogue is part of the prompt, so it is frozen before any step
   below.
2. Code tab: schema additions, move the YAML files into `scenarios/`, fix tests, generate stories for the new
   scenarios, retrain M3 (C0).
3. GPT writes test set v2.
4. Baselines on v2: flash-lite, Haiku 5.5, untrained Qwen3-4B (E12, re-scoped to v2).
5. Sonnet tab: 60-story trial, then teacher dialogues.
6. E13: LoRA on Qwen3-4B, measured on test set v2.

## 6. Consequences

- All chat numbers so far stay as the v1 record and cannot be compared with v2 numbers.
- The app, the reader's JSON schema and M3 all read the catalogue.
- The per-turn prompt grows (about 1,950 tokens today for 15 scenarios).
- Deadline is 3/12.
